# Contributing to SPIKE

SPIKE is an engineering tool. Contributions are judged first on correctness,
traceability, maintainability, and truthful capability reporting.

## Human-first requirement

The repository must remain usable without an AI assistant. A maintainer must
be able to clone, build, test, debug, and extend SPIKE using checked-in source,
documentation, fixtures, and ordinary development tools. Prompt history,
private agent memory, and generated explanations are never sources of truth.

AI-assisted changes follow exactly the same review, testing, attribution, and
validation requirements as human-written changes. Numerical code generated by
an AI requires knowledgeable human review before release.

## Development setup

Prerequisites:

- Python 3.11 or newer.
- Node.js and npm versions compatible with `app/package-lock.json`.
- Rust stable and Cargo.
- CMake 3.20+, a C++20 compiler, Eigen, and nanobind for native kernels.
- Platform WebView runtime required by Tauri.

Windows quick checks:

```powershell
python -m unittest discover -s tests\python -v
cd app
npm.cmd ci
npm.cmd run check:architecture
npm.cmd exec tsc -- --noEmit
npm.cmd run test:parser
cd src-tauri
cargo test
```

Linux uses the same commands with `npm` and the distro packages listed in
`docs/LINUX.md`.

## Change workflow

1. Read `ARCHITECTURE.md`, `docs/DESIGN_PRINCIPLES.md`,
   `docs/LANGUAGE_POLICY.md`, and the subsystem document relevant to the
   change.
2. Add or update a fixture that exposes the old behavior.
3. Make the smallest contract-compatible implementation.
4. Run focused tests while iterating, then the full required checks.
5. Update user, developer, contract, and validation documentation together.
6. Record a new ADR if a public boundary or dependency direction changes.

## Contribution licensing and provenance

Before contributing, read `LICENSE`, `LICENSING.md`, and
`THIRD_PARTY_NOTICES.md`. The workspace is mixed-license; do not assume a root
MIT grant applies to every file.

Every commit submitted for inclusion must include a Developer Certificate of
Origin sign-off in the form `Signed-off-by: Name <email>`. The sign-off certifies
that the contributor created the work or has the right to submit it under the
license recorded for that file. A future project owner may require a separate
contributor agreement for proprietary solver modules.

New source files require an approved SPDX identifier after the module's license
boundary and ownership have been reviewed. Do not add copied code, screenshots,
models, datasets, icons, fonts, board files, or binaries without recording their
source, owner, license, redistribution right, and required notices.

### Clean-room research implementation

Published research and official technical documentation may guide algorithm
selection, equations, and validation criteria, but an external implementation
is not source material for SPIKE. Independently author the derivation, data
structures, code, prose, fixtures, and test oracles. Do not copy, translate,
mechanically paraphrase, or adapt external source code, comments,
documentation, examples, meshes, or test data.

For each research-informed numerical change, record the DOI or authoritative
URL, the exact method or invariant implemented, the independent derivation and
oracle, validity limits, and a clean-room statement. A citation records method
provenance; it does not import copyright or grant dependency or redistribution
rights. Stop for owner and legal review if implementation would require
examining or adapting third-party source.

## Change gates

Numerical changes require a derivation or literature reference, units,
conditioning analysis, convergence evidence, a regression fixture, and stated
validity limits. A faster result is not acceptable if its error is unknown.

Importer changes require a real or minimal source fixture, object-count and
coordinate checks, unit checks, explicit unsupported-object behavior, and an
import-quality issue. Source parser objects must not escape the adapter.

UI changes require disabled/error/recovery states and testing at supported
window sizes. Long-running work must use the worker process and leave the UI
event loop responsive.

Packaging changes require clean-machine, offline, upgrade, and uninstall
tests. Dependency and license manifests must be updated. Commercial packaging
also requires every item in the `LICENSING.md` release gate.

## Design rules

- Depend on `DesignIR`, `AnalysisSpec`, and `AnalysisResult`, not EDA formats.
- Extend importer and solver registries instead of adding central format or
  solver switch statements.
- Keep transport, application services, numerical kernels, and presentation
  separate.
- Return structured diagnostics. Do not swallow exceptions or print success
  after a partial failure.
- Do not display inferred solver data that was not returned by a solver.
- Use stable units and document every conversion at its boundary.
- Keep new modules under the architecture size guard.
- Keep implementation inside the owning language. A new implementation
  language requires an accepted ADR and architecture-guard update.
- Do not add features to the frozen wxPython/VTK UI or domain logic to the
  thin Rust host.

Run `python scripts/check_architecture.py` before review.

## Tests and fixtures

Unit tests belong beside the language boundary they exercise. Cross-process
and project workflows belong in `tests/python`. Numerical fixtures must include
expected values, tolerances, source, and model status. Real EDA fixtures should
be redistributable and stripped of confidential data.

Tests must fail on malformed input, numerical regression, unsupported
capability claims, and contract drift. A test that only prints a discrepancy
without asserting it does not protect the product.

## Documentation

Every public feature needs:

- a user workflow or CLI reference;
- a developer/API description;
- an accuracy or behavior test;
- known limitations and recovery behavior.

Use ASCII in source and documentation unless a file has a clear need for
Unicode. Mermaid is the standard for checked-in architecture diagrams.

## Review checklist

- Does the change preserve EDA neutrality?
- Are capability and model-status claims exact?
- Can a human reproduce the result from checked-in information?
- Can failures be diagnosed without attaching a debugger?
- Does the UI remain responsive during heavy work?
- Are memory, timeout, and cancellation implications explicit?
- Are licenses and third-party obligations understood?
- Does the change stay within the accepted language budget?
- Do focused and full test suites pass?
