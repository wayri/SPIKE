## Discriminating native resource probe

Each target ran fresh and NumPy/SciPy/Shapely-loaded parents at 256 MiB, 2 GiB
and 4 GiB address-space budgets. The diagnostic attempted AS and CORE limits
only in disposable children, recorded exact admission errors and post-exec
limits, and confirmed unchanged parent limits.

| Native environment | Six AS admissions | Observation |
| --- | --- | --- |
| macOS 15.7.9 / Darwin 24.6.0 ARM64, managed Python 3.12.15 | Rejected | Even fresh Python maps about 392 GiB virtual space while using about 30 MiB resident memory |
| macOS 15.7.9 / Darwin 24.6.0 x86-64, managed Python 3.12.15 | Rejected | Fresh Python maps about 32.6 GiB virtual space |
| Linux x86-64, kernel 6.17.0-1022-azure, Python 3.12.15 | Applied | Requested AS/CORE limits persisted after exec |

Both Macs reported `ValueError: current limit exceeds maximum limit` at AS
admission. CORE disabling succeeded. These results do not establish that macOS
ignores resource limits; they establish that this absolute budget cannot be
admitted with the observed mappings. Virtual mappings are not resident RAM.

Apple's [XNU limit admission](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.101.15/bsd/kern/kern_resource.c#L1345-L1350)
rejects lowering an address-space limit below mapped usage.
[Python's subprocess contract](https://docs.python.org/3.12/library/subprocess.html#popen-constructor)
places `preexec_fn` in the child before exec. Neither reference authorizes
silently dropping memory enforcement, raising a caller's budget, or treating an
RSS watchdog as the existing hard address-space guarantee.
