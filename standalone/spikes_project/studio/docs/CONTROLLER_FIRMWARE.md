# Controller boards and native firmware

The controller library now contains **17 sourced board pinout templates** with
labeled connector pins. Open **Libraries → Controller board library** to search,
preview and place a board. Double-click a placed board to set explicit circuit
I/O bindings. Manufacturer pinout references and declared connector exclusions
remain visible in **Scope & sources**.

## Two distinct execution paths

The sampled C/C++ adapter runs user-written controller callbacks. It does not
execute MCU instructions or Arduino firmware. The separate **Simulation →
Firmware emulation** window uses the native Renode 1.17.0 instruction/peripheral
engine. There is no silent CPU or circuit-backend substitution.

Native firmware targets in this engineering preview:

| Exact board | CPU / model | Admitted image |
| --- | --- | --- |
| Nordic nRF52840 DK PCA10056 rev 3.0.2 | nRF52840 Cortex-M4 | ARM ELF32 LE or full flash-base raw `.bin` |
| Arduino Nano 33 BLE ABX00030 | nRF52840 Cortex-M4 | ARM ELF32 LE or full flash-base raw `.bin` |
| STM32F407G-DISC1 MB997 | STM32F407 Cortex-M4 | ARM ELF32 LE or full flash-base raw `.bin` |

Other catalog entries are pinout templates, **not supported binary targets**.
AVR Arduino, ESP32/C3/C6, RP2040, nRF5340 and other STM32 variants require separate
reviewed backends/platforms. Do not select a similar MCU to bypass a rejection.

## Load and run

1. Select the exact target and reviewed Renode executable. The optional runtime
   is installed separately from the Studio application; its original upstream
   license directory must remain with it.
2. Select your `.elf` or `.bin` and click **Inspect firmware**. Inspection reads
   bytes only: target memory bounds, vector table, Thumb reset/entry, ELF load
   segments and SHA-256 are checked. Files do not execute on import.
3. Review the exact firmware hash and runtime, then approve trust and click
   **Load trusted firmware**. Changing either path or target clears approval.
4. Use **Step** or **Run / Pause**. The interval is virtual time, in seconds
   (engineering suffixes such as `100u` are accepted). **Reset / reload** starts a
   fresh MCU; **Stop** closes its native process. No host GPIO, serial port,
   debug probe or network bridge is opened.
5. The GPIO grid displays actual native register samples. DI controls inject
   logical inputs. UART sends UTF-8 bytes into the model's selected UART and
   displays acquired output, bounded to 64 KiB per acquisition/display window.

Trust permits execution of a native emulator with your user permissions.
Process containment is **not a filesystem/network hostile-code sandbox**. The
adapter opens no monitor TCP port and disables CPU semihosting. Only use firmware
and runtime packages you trust. First platform loading can fetch upstream SVD
metadata into Renode's cache; subsequent cached operation is local. Offline
first-use on a clean machine has not been qualified.

## Couple GPIO to a circuit

Place one of the admitted boards. In its pin bindings use **DI** for existing
circuit nodes/reference nodes and **DO** for existing independent DC voltage
sources. Open **Native firmware emulation**, inspect/approve the matching image,
choose a sample period and click **Run with circuit**. A fresh native MCU session
runs with the owned C++ circuit engine in Continuous mode. Main-window Pause,
Resume and Stop control the coupled run. Results retain firmware, runtime and
platform hashes plus exact bindings.

The boundary is sampled DI/DO: inputs compare node voltage with VDD/2; binary
outputs drive a zero-order-held 0/VDD ideal source. The first MCU tick follows
the first accepted plant point. Sampling must be an integer multiple of the
circuit reporting interval and an integer number of nanoseconds. Only one
controller is active in a circuit run. Avoid aliasing: edges and pulses between
samples are not reconstructed. High impedance, open-drain and alternate-function
outputs are not ideal driven voltage outputs and are rejected for direct coupling.

## Executable examples

Bundled examples are under `share/spikes/examples/controller_firmware` in the
installed payload and `examples/spikes/controller_firmware` in the source tree:

- `stm32f407_gpio_rc.spksch`: GPIO-controlled RC plant. PB2 reads `sense`; PB3
  drives `VDRIVE`. Load `stm32f407_gpio_echo.bin`, then use **Run with circuit**.
  Change `VSENSE` between 0 V and 3 V with Continuous source controls.
- `nrf52840_gpio_echo.bin`: P0.2 → P0.3 logical echo plus UARTE EasyDMA byte echo.
  Advance once to initialize, drive P0.2, then step. Send one byte and advance
  virtual time to see the actual UART response. This verifies the UART register
  datapath, **not pad routing or physical UART timing**.

The original minimal firmware is reproducibly generated by
`scripts/make_spikes_firmware_examples.py`; no manufacturer SDK or binary is
redistributed in these examples. These are emulator smoke fixtures, not
deployable application firmware or hardware qualification evidence.

## Important limits and failure reporting

The manager now exposes an explicitly selected [owned native electrical-pad workflow](GPIO_PIN_WORKFLOW.md)
with labeled pin properties and separate sampled or timestamped-software-GPIO
coupling. It composes finite drivers, internal pulls, rail currents and package
R/L/C inside SPIKES. The limits below describe the legacy functional/ideal-source
workflow; electrical modes have their own explicit timing and qualification limits.

- Functional instruction/peripheral emulation is not cycle-accurate simulation,
  physical pin electronics, power consumption, thermal modeling, ADC accuracy,
  radio propagation, high-speed SPI/SI analysis or hard-real-time/HIL certification.
- The reviewed nRF model implements UARTE EasyDMA, not every legacy UART register
  or PSEL pin-mux field. Unsupported accesses fail explicitly rather than being
  silently treated as implemented. Some normal SDK binaries will therefore fail.
- In the reviewed STM32 model, whole-port ODR writes can disturb injected input
  state; the executable example uses atomic BSRR writes. General STM32 firmware
  equivalence to hardware remains unqualified.
- Application images linked above the flash base need their matching bootloader
  in a full image. Relocation, encrypted firmware, UF2/HEX, executable RAM entry,
  DWARF debugging and MCU-family substitution are not admitted in this preview.
- UART captures and process responses have explicit limits; a timeout, process
  exit or unsupported access stops the affected session. No fallback execution
  or invented signal data is produced.
